# 跨项目开发启动套件

本文整理一套与语言、框架和产品领域无关的项目启动与协作规范，目标是减少方向错误、重复返工、无法验证、状态未清理和发布不可追溯等问题。

## 一、最小项目骨架

新项目初始化时，建议建立与团队规模相称的最小文档和自动化骨架：

```text
PROJECT_RULES.md       # 仓库级硬约束，短而明确
CONTRIBUTING.md        # 日常协作入口
变更请求模板          # 目标、风险、验证和回退
持续集成配置          # 最小构建、测试和静态检查
docs/
  product/             # 目标、范围和非目标
  architecture/       # 当前架构和边界
  decisions/           # 已确认的关键决策
  plans/               # 可执行计划和状态
  operations/          # 安装、运行、排障和验收
  research/            # 外部调研和实验结论
  releases/            # 版本说明
scripts/               # 可重复的开发和验证命令
```

入口规则文件只保留所有任务都必须遵守的规则；产品事实、架构细节和模板放到对应文档，避免入口文件变成无法维护的百科全书。

## 二、变更流程

1. 先读取产品范围、架构文档和现有调用链。
2. 对问题先记录复现证据、根因假设和影响范围，不直接编辑代码。
3. 提出文件级方案、状态转换、测试清单、兼容性和回退方式。
4. 复杂变更先进行独立方案审查，确认后再实现。
5. 所有变更从受保护的稳定分支创建独立分支，禁止直接修改受保护分支。
6. Commit 按可独立测试、审查和回退的逻辑单元拆分。
7. PR 必须说明背景、用户可感知变化、不包含范围、风险、验证结果和发布说明草案。
8. 合并、删除、标签和发布属于不可逆操作，应单独确认并保留记录。

## 三、测试与质量门

默认采用“失败测试 -> 最小实现 -> 全量回归 -> 提交”的循环。测试应覆盖正常路径、每类失败、超时/过期、重复进入和中断后恢复。

质量门至少分三层：

- 快速单元测试：每次开发和 PR 执行。
- 构建、集成、安装和脚本测试：验证模块间契约。
- 真实环境或人工验收：需要真实设备、GUI、权限或外部服务时执行，并明确标注 CI 未覆盖部分。

每个验证命令都应可重复；失败输出至少包含阶段、退出码、脱敏摘要和下一步。

## 四、日志与隐私

日志可分为操作摘要、失败诊断和显式开启的完整轨迹三层。默认日志应回答“哪次操作、做了什么、前置条件怎样、在哪个阶段失败、最终状态是什么”，但不记录敏感正文、凭据、认证材料、完整隐私数据或无上限调试输出。

## 五、可复用的工作能力

按问题选择能力，不必全部启用：

| 能力 | 适用时机 | 产出 |
|---|---|---|
| 测试驱动开发 | 新功能、缺陷修复、集成测试 | 从失败测试到回归验证的闭环 |
| 证据驱动诊断 | 报错、失败、性能回退 | 复现、根因、影响范围和验证结论 |
| 双轴代码评审 | 分支、PR、WIP 评审 | 规范符合性与需求符合性问题清单 |
| 接口与模块设计 | 模块边界、可测试性或 API 选择 | 责任边界、候选方案和取舍 |
| 领域建模 | 术语混乱、跨团队协作 | 统一词汇、实体关系和决策记录 |
| 原型验证 | 状态模型或交互尚不确定 | 可丢弃的技术或交互验证 |
| 一手资料研究 | 外部项目、规范、API 调研 | 可追溯来源和适用边界 |
| 增量重构规划 | 大型重构、需要拆小提交 | 可独立验证和回退的步骤 |
| 提交前门禁 | 项目稳定后 | 格式化、类型检查和测试自动执行 |
| 安全威胁建模 | 明确的安全评估需求 | 信任边界、攻击路径和缓解措施 |

## 六、新项目首日清单

- 写清产品目标、非目标和当前版本范围。
- 画出模块/进程边界，确定配置和副作用的责任方。
- 建立规则文件、贡献指南、变更模板和最小 CI。
- 为主要命令提供构建、测试、静态检查和健康检查入口。
- 先为一个正常路径和一个失败路径补测试，再扩展功能。
- 需要外部事实时建立带来源的研究记录；不确定的接口或交互先做可丢弃原型。
- 首次发布前补安装、排障、人工验收和回滚说明。

## 七、落地方式

建议维护一个独立的项目模板，包含精简规则文件、变更模板、质量门和脚本占位符；新项目只需补充产品、技术栈和发布规则。自动化能力按项目需要启用，不把领域实现写进通用模板。
