## 1. 目标

本路线图用于定义 GestureKit 在当前 V1 基线上的后续优化顺序、阶段边界、并行规则和阶段验收标准。

路线图目标：

- 在不扩大 V1 范围的前提下，优先补齐自用闭环。
- 同步补最必要的开源准备，避免后续仓库整理返工。
- 用任务级粒度表达下一阶段工作量，便于直接排期或继续细化为实施计划。

## 2. 约束

后续优化必须继续遵守以下边界：

- 不引入多浏览器支持。
- 不引入完整规则编辑器。
- 不引入通用 App 自动化。
- 不把扩展侧设置扩展为任意动作绑定。
- 不改变 `connectNative()` + native host shim + App IPC 的既定通信边界。

如果后续优化需要突破以上边界，必须先更新契约或技术设计，并获得确认，再进入实现。

## 3. 分期原则

本路线图采用“主线串行 + 低耦合并行”策略。

主线顺序：

```text
P3 -> P4 -> P5 -> P6
```

排序原则：

- 优先做能降低后续验证成本的工作。
- 优先做能直接提升日常自用体验、且不显著扩范围的工作。
- 把最容易扩大范围的能力放在最后。

并行原则：

- 有明显依赖关系的任务保持串行。
- 文件边界清晰、验收边界独立的低耦合任务允许并行。
- 每个阶段必须可以独立验收，不接受积压到最后统一验证。
- 并行任务不得同时修改同一组核心边界文件，尤其是协议、规则引擎、安装入口和 popup 主状态流。

## 4. P3 安装与验收闭环

### 4.1 阶段目标

把 GestureKit 的本地安装、连接配置和基础验收流程收敛成低摩擦、可重复、可诊断的闭环，减少后续功能调试时的环境噪音。

### 4.2 范围

P3 只解决安装链路、配置链路、smoke check 和故障排查入口，不新增用户手势能力。

### 4.3 任务

1. 增加 native host manifest 生成脚本，输入扩展 ID 和 host 路径，输出可直接安装的 manifest。
2. 增加本地安装命令入口，收敛 manifest 拷贝和目标目录写入。
3. 增加本地 smoke check，至少覆盖 `GestureKitHost --self-test`、`GestureKitApp` 可启动、Chrome extension 可构建，以及一条端到端连通探针，验证 `connectNative()`、host manifest 注册、stdio 桥接和 App IPC 监听链路可用。
4. 重写安装文档，明确区分首次安装、扩展重建后的刷新步骤和常见更新路径。
5. 补一份连接问题排查说明，能快速判断故障落在 App、native host、extension 或 manifest 配置。

### 4.4 验收

- manifest 安装不再要求手工编辑 JSON。
- 文档或脚本能指导干净环境完成首次安装。
- 能通过固定命令快速验证 host、app、extension 以及 `connectNative()` 到 App IPC 的整条链路是否健康。
- 常见连接失败能够映射到明确排查入口。

## 5. P4 推荐应用闭环

### 5.1 阶段目标

把现有诊断和推荐展示推进到“用户可以显式应用推荐，并且知道应用结果是否真实生效”。

### 5.2 范围

P4 默认以“应用推荐设置”为核心，只处理推荐写回、确认、同步状态和失败语义，不重复扩做已完成的诊断展示能力，也不新增新的动作类别或规则系统能力。

### 5.3 任务

1. 在 popup 中增加“应用推荐设置”入口。
2. 在应用前增加显式确认，只允许修改轻扫灵敏度和相关阈值，不改规则绑定。
3. 明确推荐应用后的所有权和持久化语义：扩展侧哪些值持久保存在 `chrome.storage.local`，App 侧哪些值只作为运行时已应用状态，`settings_ack` 表达的“已应用”具体指什么。
4. 应用后在 popup 中显示同步成功、失败原因和当前生效值，并区分“已保存到扩展设置”和“App 运行时已应用”。
5. 扩展复制诊断输出，补充“当前设置 vs 推荐设置”的差异摘要。
6. 补一轮推荐逻辑边界测试，避免在失败原因不明确时给出误导性调参建议，并覆盖 App 重启、host 重连或 ack 缺失时的状态表现。

### 5.4 验收

- 用户能在 popup 中看见推荐并主动应用。
- 推荐应用结果在 UI 和诊断摘要中可见。
- 推荐失败不允许静默处理，必须返回明确原因。
- “已保存”与“已应用”状态语义明确，且不会把最后一次 ack 误显示成持久生效。
- 推荐应用后不突破现有规则 source of truth 边界。

## 6. P5 菜单栏状态与生命周期加固

### 6.1 阶段目标

在现有菜单栏 App 基础上补齐状态可见性、生命周期控制和排障入口，同时保留现有 Runtime/Core 边界。

### 6.2 范围

P5 聚焦菜单栏状态增强、排障入口和生命周期加固，不重写手势识别主流程，不引入复杂桌面 UI。

### 6.3 任务

1. 加固现有菜单栏状态文案和图标反馈，明确 App 监听状态、扩展连接状态和最近错误摘要。
2. 在菜单栏中补齐日志入口、安装说明入口和常见排障入口。
3. 提供启动监听、停止监听、重启 App 本地监听或刷新状态等基础菜单项；不把 native host 生命周期控制错误地下放给 App。
4. 维持现有 `Runtime`、`GestureRecognizer` 和 `GestureKitCore` 边界，不把 UI 状态逻辑反向压入识别层。
5. 为后续自启动、打包和签名预留结构，但不在本阶段完成完整分发链路。

### 6.4 验收

- 日常使用时不需要长期盯终端输出。
- 连接状态和关键错误可从菜单栏直接判断。
- 原有终端运行方式仍可用于调试，不与菜单栏主入口冲突。
- 菜单栏实现不引入新的规则硬编码或协议耦合。

## 7. P6 开源最小准备

### 7.1 阶段目标

在前 3 个阶段稳定后，完成最小必要的仓库开源整理，降低外部理解和本地启动门槛。

### 7.2 范围

P6 只处理仓库整理、模板化、脱敏和贡献说明，不在本阶段引入新的用户可见动作。

### 7.3 任务

1. 整理安装模板、manifest 模板和排查文档，使外部开发者可以理解并按文档启动。
2. 做一轮仓库脱敏检查，排除本机路径、个人扩展 ID、日志或临时配置残留。
3. 补最小贡献说明和开发前提，明确当前实验性质、平台限制和非目标。
4. 校验中文优先文档、模板占位符和开源边界说明是否一致。

### 7.4 验收

- 仓库文档足以支持外部开发者完成基础理解和本地运行。
- 不引入多浏览器支持、复杂规则配置或通用自动化承诺。

## 8. P7 候选动作扩展

### 8.1 阶段目标

如果 `P3-P6` 稳定完成，且用户明确要求扩动作，可把新增浏览器动作作为独立候选阶段评估。

### 8.2 范围

`P7` 默认不自动启动。任何新增用户可见动作都必须先更新契约或技术设计，并获得确认，再进入实现。

### 8.3 候选任务

1. 评估 1 到 2 个高频浏览器动作，优先考虑“恢复刚关闭标签页”等低认知负担动作。
2. 新动作必须通过 `RuleEngine` 和 Chrome action executor 接入，不允许走 UI 特例或输入层硬编码。
3. 为新动作补齐行为测试、诊断状态和文档说明。

### 8.4 验收

- 已完成契约或设计变更并获得确认。
- 新动作不破坏现有 V1 手势和规则边界。
- 不借由新增动作引入多浏览器、复杂规则配置或通用自动化承诺。

## 9. 并行建议

推荐并行方式如下：

- `P3` 主线推进时，不并行推进 `P5` 的 App 生命周期改动，避免把安装/启动/连接回归混在一起。
- `P4` 推进时，可并行补齐 `P3` 的排查文档、模板文档和安装文字收口。
- `P6` 可在 `P5` 进入收口阶段后并行推进文档脱敏和模板化，因为两者文件边界更清晰。
- `P7` 不建议在 `P3-P6` 未稳定前提前开启，以免新增动作掩盖安装或诊断问题。

不推荐的并行方式：

- 同时推进安装入口重构和协议层重构。
- 同时推进 popup 主状态流大改和菜单栏状态流大改。
- 在推荐逻辑尚未收敛前同步扩多种新动作。

## 10. 推荐执行顺序

如果希望控制单次工作量，同时尽量多拿下几个收益明确的小项，建议按以下顺序执行：

1. 先完成 `P3` 中的 manifest 生成、安装入口和 smoke check。
2. 接着完成 `P4` 中的“应用推荐设置”闭环。
3. 然后推进 `P5` 的菜单栏状态与生命周期加固。
4. 再完成 `P6` 的开源最小准备。
5. 最后再决定是否开启 `P7` 候选动作扩展。

其中最适合先连续拿下的小组合是：

- `P3-1` manifest 生成脚本
- `P3-2` 本地安装入口
- `P3-3` smoke check
- `P4-1` 推荐应用按钮
- `P4-2` 应用前确认和结果显示

这组工作量相对可控，且能明显提升“装起来”和“调顺它”的效率。
